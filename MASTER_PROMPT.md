# AI coding-tool prompt: gnkalgo phases 1 + 2

Act as a principal full-stack engineer and cybersecurity architect experienced with Indian retail trading APIs. Build `gnkalgo` as a production-oriented, open-source TypeScript/Node.js service using Fastify and PostgreSQL. Write original code only; do not reproduce licensed commercial source. Treat official broker, exchange, and SEBI documentation as authoritative and cite the exact version/date used.

Implement account creation by either Google Identity Services or E.164 mobile plus Twilio Verify OTP. Model a stable `users` record with separate unique `user_identities`, allowing a deliberately authenticated linking flow without accidental identity merging. Seed `gnkalgo.admin@gmail.com` as the initial admin, but never bypass provider verification or create a default password. Use opaque, hashed, revocable server sessions in Secure/HttpOnly/SameSite cookies. Do not store auth tokens in browser storage.

Implement a configuration-driven broker adapter boundary for Dhan, Fyers, Zerodha Kite Connect, Angel One SmartAPI, and Upstox. Enable an adapter only if its current official approved API supports broker-hosted authorization. Provide `GET /api/v1/auth/redirect/:broker`, which creates a cryptographically random, single-use, hashed, ten-minute OAuth state tied to the authenticated user and broker and redirects only to a configured allowlisted broker URL. Provide `GET /api/v1/auth/callback/:broker`, which validates and atomically consumes state, exchanges the single-use code server-side through a required static-IPv4 egress proxy, and upserts the daily token. Correctly isolate broker-specific semantics; do not falsely label nonstandard handshakes as standards-compliant OAuth 2.0. Never collect broker password, PIN, OTP, or TOTP and never use headless browser automation. Broker-hosted 2FA must remain in the redirect flow.

Provide `POST /api/v1/trades/kill-switch`, requiring an authenticated user and explicit confirmation, that atomically blocks that user's workers, deletes all current tokens, records a secret-free audit event, and attempts official broker-side revocation when supported. Explain that it cannot recall exchange-accepted orders. Disallow refresh-token persistence and refresh loops. Purge access tokens and vendor-key instances at 15:30 Asia/Kolkata with both an idempotent external scheduler and startup/minute reconciliation.

Create complete SQL migrations for users, identities, sessions, OTP attempts, OAuth states, `user_broker_tokens`, worker kill state, and security audit events. Include `broker_name`, `client_id`, `encrypted_access_token`, `token_generated_at`, `session_expiry_timestamp`, `encrypted_vendor_key`, encryption key version, constraints, and indexes. Encrypt tokens and vendor keys using AES-256-GCM with random 96-bit nonces, authentication tags, field/user/broker AAD, and KMS/HSM-backed versioned keys. Include a rotation procedure; never log plaintext secrets.

Add schema validation, generic anti-enumeration errors, strict callback allowlists, origin/CSRF defense, CSP/security headers, body limits, request timeouts, and distributed Redis rate limits by IP, phone hash, user, and broker. Mask emails and phones and structurally redact authorization headers, cookies, OTPs, query codes, states, access tokens, client secrets, vendor keys, and encryption keys. Define audit events without PII. Trust forwarded IPs only from known ingress addresses.

Force every broker-bound token and order request through a dedicated egress/NAT or HTTPS proxy whose public static IPv4 is broker-whitelisted; fail startup in production without it and recommend network policy that blocks direct egress. Add health checks that do not expose secrets.

Provide a minimal frontend showing the official GIS button, credential POST, OTP request/verify form, accessible errors/countdown, broker connect buttons, callback result, session handling, and a strongly confirmed kill-switch control. Use same-origin secure cookies.

Deliver a modular repository tree, environment template, migrations, implementation, unit/integration tests, mocked provider contract tests, Docker development setup, CI for lint/typecheck/test/dependency/secret scanning, deployment notes, key rotation, rollback, observability, incident response, and a threat model. Do not claim “SEBI compliant” merely from code. Identify controls requiring broker approval, exchange registration, infrastructure validation, operational procedures, or legal review. Ask before adding live-trading or order-placement capability.
